# WF1 Phase B with native tools and saved workflows

This is the current implementation. Import `../wf1_ticket_intake_and_dispatch.json` as the main WF1 and the seven JSON files in `workflows/` as saved helper workflows. The helpers are normal n8n workflows whose nodes can be opened and inspected in the editor. There is no embedded `workflowJson`, no workflow generated by the model, and no `next_actions` list returned to the agent.

The first 15 current Phase A nodes and their outgoing connections are preserved, including the project's newer EXIF-based image preparation. WF2, `schema.sql`, the existing Python services and `phase_b/original_wf1.json` are unchanged. The earlier Word guide describes the dispatch architecture; the [technical knowledge supplement](../knowledge/README.md) describes the newly added native Supabase/OpenAI nodes, read-only source service and synchronization workflow.

## What changed

| Operation | Current implementation |
|---|---|
| `create_ticket` | Native Postgres AI tool; fixed parameterized SQL creates or recovers the current ticket and records source identity. No JavaScript wrapper or child workflow. |
| `get_context` | Native Postgres AI tool; fixed read-only SQL returns ticket facts, deadlines, response counts, candidate order and notice keys. |
| `initialize_dispatch` | Calls saved workflow **Dispatch - Initialize Ticket** to initialize the shortlist, appointment and pending opening notice after ticket creation. |
| `send_offer` | Calls **Dispatch - Send Technician Offer**, with a model-supplied `technician_id` checked against the next eligible shortlist member and `knowledge_chunk_ids` rechecked in Supabase before source excerpts enter the invitation. |
| `Radiator Technical Knowledge` | Direct native Supabase Vector Store tool with native OpenAI Embeddings; searches only the current ticket's exact IFC object and current published sources. |
| `send_notice` | Calls **Dispatch - Send Notice**, with a model-supplied `notice_key` chosen from pending notices. This covers the FM opening and subsequent notices. |
| `process_events` | Calls **Dispatch - Process Responses** to apply persisted responses, expire offers, commit one winner and queue notices. |
| `escalate` | Calls **Dispatch - Escalate Ticket** to record justified escalation and queue its FM notice. |

Two additional helpers are called on fixed execution paths, not exposed as agent tools: **Dispatch - Record Email Receipt** records the Gmail result; **Dispatch - Record Incomplete Execution** records failed or unfinished invocations.

## Agent responsibility and remaining constraints

The agent now decides its tool calls from current facts and the task objectives. It supplies actual inputs for the offer and notice tools. There is no code-generated operating script telling it which tool to call next. Returned `outcome` and numeric counts support independent completion checks; they are not a sequence of operations.

Autonomy still has clear limits. The agreed shortlist order, deadlines, offer capacity, recipients and one-winner rule are enforced by SQL and policy code. The agent cannot choose an arbitrary technician or negotiate a different appointment. These are required business constraints. Incorrect candidate or notice inputs return a rejection reason and cause no unauthorized send.

The model remains `claude-sonnet-4-6`, temperature 0, output limit 2,000 tokens. The agent iteration limit is now 24, allowing separate creation, initialization, reads and notices. The output limit applies per model response, not to the whole invocation. The system message is in `system-message.txt`.

Persistent business memory remains PostgreSQL, exposed through the native `get_context` tool. No conversational memory node is attached. The returned context omits tokens, email bodies and deployment configuration. This is durable ticket state, not a transcript of earlier model conversations.

## Why some work still uses a saved workflow

Creating a ticket and reading context are direct native Postgres tools. Creation uses Execute Query rather than an unguarded Insert because source reuse and duplicate protection must be coordinated without changing the existing schema. The query is visible in the tool and its data is passed as parameters; the model does not write SQL.

Email delivery is a coordinated task: reserve a message or offer, commit that reservation, send through the native Gmail node, then record the result. A direct Gmail tool alone would not provide those guarantees. The native Gmail send is visible inside the two sending workflows. Automatic node retries are disabled for Gmail; retrying a database conflict does not resend a committed message.

JavaScript has not been eliminated. `operations.js` separates initialization, offer reservation, notice claiming, response processing, escalation, receipt handling and failure handling into individual functions. The builder includes only the selected operation and its dependencies in each helper. Read-only state access moved to native SQL, runtime rewriting of Code nodes was removed, and one shared receipt workflow replaces repeated acknowledgement branches. Atomic state commits and bounded conflict retries remain necessary.

## Calling a saved workflow

For a simple ticket insert, the current path is:

```text
WF1 Dispatch Agent
  -> create_ticket native Postgres tool
  -> ticket_id
```

For coordinated offer delivery, the implemented path is:

```text
WF1 Dispatch Agent
  -> send_offer workflow tool
     ticketId and sourceKey bound by WF1
     technicianId selected by the agent
  -> saved workflow Dispatch - Send Technician Offer
     When Executed by Another Workflow
     -> Load Ticket State
     -> Reserve Technician Offer
     -> State Changed? -> Commit Change -> Commit Succeeded?
        conflict -> Retry Conflict -> reload
     -> Email Claimed? -> Gmail - Send Claimed Email
     -> Record Gmail Receipt [saved helper]
     -> Return Current Context
```

Each helper starts with **When Executed by Another Workflow** and defines explicit input fields. Its last node returns a context object to the caller. No additional public webhook is needed for these internal calls.

The five tools attached to the agent use **Call n8n Workflow Tool**, Source **Database**, to select saved workflows by ID. Here Database means n8n's saved-workflow storage, not the maintenance PostgreSQL database. The model decides when to call these tools. The receipt and incomplete-execution helpers instead use ordinary **Execute Sub-workflow** nodes: they run when execution reaches that fixed step and wait for their results. The agent cannot supply or fabricate a Gmail receipt through a tool.

## Preserved dispatch rules

| Ticket | Concurrent offers | Expiry | Appointment |
|---|---:|---|---|
| Ordinary severity 1–3 | 1 | 48 elapsed hours from the recorded send acknowledgement | Fixed business-day afternoon, 14:00–16:00, after the response window |
| Urgent severity 4–5 | Up to 2 | Earlier of 48 hours or appointment start | Original next-business-day 08:00–10:00 slot, never postponed |

SENDING, LIVE and UNCERTAIN occupy offer capacity. First valid persisted acceptance wins one assignment; competing offers are withdrawn. Declined or expired candidates are not invited again for that ticket. Eligibility is checked again on acceptance. The initial shortlist has five technicians, filtered by active status, matching skill and building-A, ordered by fewest open jobs, oldest assignment with never-assigned first, highest rating and ID.

Ordinary replacement offers get a full new 48-hour window and an appropriate fixed afternoon slot; the original date is retained when suitable. The calculation includes a ten-minute send margin. Unusually long Gmail acknowledgement delays still require operational review. Business days exclude weekends, not public holidays; timezone and daylight saving handling use Europe/Rome.

## Entry routes and waiting

New reports still enter through the original Google Drive trigger and Phase A. Clicking an email link uses the GET **Offer Confirmation Page** webhook to display a read-only form. Submitting that form uses POST **Offer Response Submission**, which records the validated response before invoking the agent. Opening a page alone cannot assign a ticket.

GET and POST use the same `/cbm-wf1-offer` path, distinguished by method. `callbackBase` is the public production prefix, for example `https://n8n.example.org/webhook`. Do not append the endpoint twice. The child workflows do not use that public URL to call each other.

The recovery schedule checks every minute and selects at most one due ticket. Idle checks do not invoke the LLM. Expiry is enforced in callback SQL even if a recovery backlog delays notices. A native-created ticket whose initialization was interrupted becomes eligible for recovery after a minute; three recorded initialization failures require operator attention. The existing initialized-state failure counter remains cumulative.

The missing-receipt gap in the earlier design is addressed: native context reads now identify overdue SENDING claims after five minutes. Verification routes those cases through the fixed failure helper, which persists UNCERTAIN state and the halt. No new automatic send is allowed while delivery is unresolved.

## Configure and import

1. Keep `deployment.local.json` private. Set the Postgres, Gmail and Anthropic credential references, FM address, public `callbackBase` and model there. The tracked exports are templates produced from `deployment.example.json`; Phase A has its own pre-existing configuration and is not configured by this file.
2. From `phase_b`, run `node .\build-workflow.js .\deployment.local.json` to generate locally configured WF1 and all seven helpers. This rewrites deployment references in the generated exports; do not commit private configured exports. Running `node .\build-workflow.js` produces the tracked templates again. The builder refuses to overwrite changed preserved Phase A nodes or connections.
3. Import the seven files under `workflows/` into the intended n8n project. Use `workflow-manifest.json` to identify their names, IDs and files. Configure and check the credentials in these saved workflows.
4. Verify workflow IDs after import. If the instance assigns different IDs, put the actual IDs under `workflowIds` in `deployment.local.json`, using the operation keys in the manifest, rebuild and update the existing helper workflows and WF1. Alternatively, select the actual saved workflows in the five agent tools, the main Record Incomplete Execution node, and the Record Gmail Receipt node in each sending helper. Refresh/check input mappings. A template ID alone does not prove that a saved workflow exists in your instance.
5. Publish the saved helpers needed in production. The current n8n documentation requires publication for saved workflows invoked through the agent's workflow tool. Receipt and failure helpers must also be callable by their parents under the instance's workflow permissions. All exports are delivered inactive for configuration and review.
6. Import or update the intended WF1, preserving any instance-specific Phase A settings. Compare it with your live export before replacing that workflow: the repository's Phase A is preserved exactly, but it may still contain template values. Verify node availability, credentials and helper references. Test with a separate database and controlled mailbox before publishing WF1. Do not leave old and new WF1 intake versions active together.

No schema migration is required. Existing CBM_SOURCE, CBM_DISPATCH_STATE and CBM_RESPONSE records are reused. CBM_INIT_FAILURE is an additional event type in the existing ticket_events table. Version-1 dispatch snapshots remain readable. Before changing a live deployment, reconcile outstanding uncertain deliveries and verify that the stored FM/callback configuration remains appropriate for outstanding offers.

## Validation and limits

Run `node .\setup-test-runtime.js` once to install the ignored test runtime, then `node .\test-dispatch.js`. The report is written to `validation-report.json`. Tests use PGlite 0.5.8 with the actual schema and SQL. They execute saved workflow graphs and the nested receipt helper with mocked Gmail, checking native creation/read, explicit tool inputs, bound ticket identity, helper references, race protection, the 48-hour policy, urgent cutoffs, recovery and preservation of Phase A/WF2/schema.

These are not live n8n-engine, real Anthropic or Gmail tests. Model tool selection is simulated; concurrent writes use overlapping snapshots rather than two independent PostgreSQL server sessions. Import and production execution still need verification in your n8n instance. A model can choose an invalid tool call or exhaust its iteration limit; the post-agent verifier checks committed state independently.

Gmail and PostgreSQL do not share a transaction, so exactly-once email delivery is not guaranteed. A missing or ambiguous provider receipt halts ordinary sends. An operator must reconcile the existing claim and provider records before resending, then deliberately clear the halt after all uncertainties are resolved. This package does not add an operator recovery UI. A confirmed Gmail message ID proves provider acceptance of the send, not recipient delivery or reading.

WF2 still references some columns absent from schema.sql, including after_file_id, verification, closed_at, ifc_version and technician jobs_completed. This pre-existing issue is outside the Phase B refactor. Errors before the verification branch can still stop an execution without reaching the FM error notification.

## Source files

`build-workflow.js` assembles the preserved main workflow and exports helpers. `saved-workflows.js` defines the visible helper graphs and explicit mappings. `operations.js` contains individual guarded state operations. `queries.js` contains native database queries. `system-message.txt` configures the agent. `original_wf1.json` is a required baseline for rebuilding WF1 and checking that Phase A is preserved. Import the generated main WF1, not this baseline.
